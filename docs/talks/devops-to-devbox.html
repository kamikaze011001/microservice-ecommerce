Code has zero value
until it runs for users.

A finished feature on a branch, a passing test suite, a merged PR — none of it helps a customer yet. Everything between “merged” and “running, and staying up” is where teams lose weeks.

Set the frame: the unit of value is software running in production, not code written. Ask the room: how long from merge to “a user can use it” for us today?

DevOps: you build it, you run it.

Not a job title or a tool — a way of working where the people who change the system also own how it behaves in production.

01

Flow

Small changes, built and deployed automatically. CI/CD so “release” is boring, not an event.

02

Feedback

See what your change does in production — metrics, logs, alerts — minutes after shipping, not weeks.

03

Learning

Incidents become blameless postmortems and fixes to the system, not blame for a person.

“You build it, you run it” — Werner Vogels (Amazon CTO), 2006. The word DevOps came from Patrick Debois’ DevOpsDays, 2009. The three ways (flow, feedback, learning) are from The Phoenix Project / DevOps Handbook.

Both sides are rational. Dev is rewarded for change; Ops is rewarded for nothing changing. One side’s success is the other side’s risk — so the code gets thrown over the wall and the pager rings on the other side.

DevOps said “tear down the wall.”
It didn’t say how.

“Give developers production” doesn’t scale — not everyone can be an expert in Kubernetes, Kafka, Vault and on-call. So the industry found two concrete routes.

The naive version of DevOps — every dev does everything — burns people out (cognitive load). That’s the bridge to the two answers: SRE and platform engineering.

to real DevOps

SRE makes reliability a number both sides agree on.

Same goal — ship fast AND stay up — attacked from two sides. SRE from production backwards; platform engineering from the developer forwards.

SRE: turn the fight into a number.

“What happens when you ask a software engineer to design an operations function.” — Google, 2003

99.9%
An SLO — the reliability users actually need.
The other 0.1% is the error budget: about 43 minutes a month.
budget used this month · 62%43 min
Budget left?Ship. Take risks. Deploy on Friday if you want.
Budget burned?Feature freeze — the next work is reliability.
Toil capped at 50%Ops work beyond that becomes engineering work: automate it.
The genius: Dev and Ops stop arguing opinions. 30 days × 0.1% = 43.2 min. Both sides own the same budget. Other SRE tools: on-call, blameless postmortems, SLIs from real user traffic. Quote: Ben Treynor Sloss, Google SRE book.

Key ideas: golden paths (opinionated, supported, optional), self-service (no ticket to another team), platform as a product (devs are customers; if they don’t use it, it failed), lower cognitive load (Team Topologies, 2019).

Not either/or. Big companies run both: the platform makes it easy to build reliable services; SRE keeps them reliable. Many platforms ship SLO tooling as one of their golden paths.

We started with platform engineering.

SRE needs production traffic to measure. Our pain is earlier: getting a prod-like environment, testing a change in it, and knowing what broke — before anything reaches production.

So we built the platform first — and gave it room to grow SRE tools later.

Honest framing: we’re not running a big production yet. The highest-leverage problem is developer friction and late feedback. The chaos run is a taste of SRE thinking (invariants, budgets) running on top of the platform.
04

GitOps

Git is the source of truth. The cluster follows it — automatically, all the time. Deploy, rollback and config become commits.

Before the devbox, the engine under it. Yes — this project runs on GitOps: Argo CD reads two git repos and makes Kubernetes match. Everything in part 05 is a UI on top of this.

The four are the OpenGitOps principles (CNCF, v1.0). The key shift is direction: nothing outside the cluster needs cluster credentials, and the agent never stops comparing — so a manual change can’t quietly stick.

Sync: git vs live, every 60 s.

Desiredgit: chart + values

Syncedlive matches git. Healthy is separate: pods ready, rollout done.
selfHealsomeone runs kubectl set image → put back to git’s version.

refreshArgo polls every 60 s; the portal nudges it right after a commit.
Synced vs Healthy is the distinction people mix up: Synced = the YAML matches; Healthy = it actually works. A deploy of a broken image is Synced but Degraded. Our devbox-proof checks self-heal by doing a kubectl set image behind git’s back and waiting for Argo to undo it. Values from deploy/devbox/applicationset.yaml and argocd-values.yaml.

Each Application renders apps/ with onlyService=<svc>: the how (chart) from the code repo, the what (versions, config) from the env repo. Add a service = add a file. Add an env = add a folder.

“Metachart” = our umbrella Helm chart: one chart for the whole system, infra and apps as subcharts, the same chart for local k8s and AWS (envs/*.yaml). The ApplicationSet’s git generator turns every services/*.yaml into one Argo CD Application. Why per service: each gets its own health, history and rollback — roll back order-service without touching inventory. Honest note: infra (databases, Kafka) stays on make, not Argo — shared by every env.

Tags are commitse3996eb = the git commit it was built from — immutable, traceable, same inputs never rebuilt.
The old image is still thereregistry cleanup never deletes a tag an env still pins.
Argo does the restcommit → sync → rolling update; history shows who rolled back what.
41 smeasured: rollback to Healthy
No special rollback tool, no kubectl, no remembering the last good tag: the env repo history IS the list of good tags. Per-service Applications mean the rollback touches one service. 41 s is from the startup-probe change: rollback converged in 41 s with 0 restarts. The portal’s Deploy dropdown is just a nicer way to write this diff.
05

Devbox

Our internal developer platform. A production-like copy of the whole system on every laptop — and one portal to drive it. Every change is a git commit.

Everything in this part is a UI over part 04’s GitOps. Assembled, not invented: Argo CD (GitOps), Gitea (local git), a registry, VictoriaMetrics + Grafana, k6, Bruno — plus one small portal that ties them into golden paths.

How it fits together.

Youbrowser · git push
Devbox portalenvs · build · settings · API & perf tests · topology · logins
Gitea · env repowhat runs where — every deploy and setting is a commit
Runner jobscreate/delete env, build, k6, Bruno — the same scripts as the CLI
VictoriaMetrics + Grafanaevery perf run, tagged with its versions
Argo CDmakes the cluster match git
Kubernetesprod-like · preview-cart · preview-ui …
each env: own namespace, databases, topics, Redis
Registryevery image, tagged by commit
Read it left to right: you act in the portal; changes become commits in the env repo; Argo CD sees the commit and makes the cluster match. Long work (create an env, build an image, run k6) runs as a Kubernetes Job using the same proven scripts. That’s GitOps: git is the source of truth, history and rollback come for free.

The GitOps payoff: there is no special rollback mechanism. Deploying the previous tag is a commit; Argo CD makes the cluster match. The env repo is the audit log — nobody has to remember what they ran.
