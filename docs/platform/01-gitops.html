GitOps: git says, the cluster does

Phase 1 of the devbox. Argo CD now deploys every service from a git repo, so what runs is always what's committed.

Devbox · platform engineering series · 1 / 6
Big ideaThe mapThe loopVocabulary In this repoWhat brokeTry itInterviewNext

Before: you tell the cluster what to do — helm upgrade, kubectl edit. The cluster's state is the sum of every command anyone ever ran.

After: you write down what you want in git. A controller keeps the cluster equal to it, forever.

That swap — from push commands to pull desired state — is all GitOps is. Everything else (history, rollback, audit, drift repair) falls out of it for free, because git already does history and rollback.

The two edits that look the same have opposite outcomes. A kubectl edit creates drift — self-heal reverts it. A commit changes the truth — the cluster follows. That's why "change it in git" isn't a ceremony: it's the only change that sticks.

3Vocabulary you'll see in the UI

Application

One unit Argo CD reconciles: a source (repo + path + values) → a destination (cluster + namespace).

Here: prod-like-order-service = the apps chart, narrowed to order-service, into apps.

ApplicationSet

A factory for Applications. A generator lists things (files, folders, clusters, PRs); a template stamps one Application per item.

Here: the git files generator over envs/*/services/*.yaml. New file → new Application.

Sync status

Synced = live equals git. OutOfSync = they differ (a new commit, or drift). Says nothing about whether the app works.

Health status

Healthy / Progressing / Degraded / Missing — does the thing actually run? A Deployment is Healthy when its new pods are Ready.

Synced + Degraded = "git was applied, and what git says is broken".

selfHeal

When live drifts from git without a commit, put it back. On here.

prune

When something is removed from git, delete it from the cluster. Without it, deleting a service file would leave the service running forever.

Multi-source

One Application, several repos. One renders; another only supplies values (ref: env → $env/…).

Here: chart from microecom, values from env-config. HOW and WHAT change at different speeds, so they live apart.

App repo vs config repo

The classic split. App repo: code + templates, changes with features. Config repo: which version runs where, changes with deploys.

Here: the config repo is local (Gitea) because your deploys are experiments, not GitHub history.

5What broke while building it

A null that only works inside an umbrella chart

Symptom: rendered per service, mock-paypal-service got VAULT_TOKEN and SPRING_CLOUD_VAULT_URI — vars its values explicitly unset with null.

Cause: Helm keeps a default null when the chart is merged in as a subchart, but deletes the key when the chart renders on its own — which is exactly what each Argo CD Application does. The template never saw the "unset".

Fix: "" instead of null (the template already drops any empty value). Caught by the parity test, not by eye — the two renders differed by four lines out of ~1,500.

Two managers, one object

Risk: if make k8s-apps-helm already installed the apps, Argo CD would adopt the same Deployments; every helm upgrade and every Argo CD sync would then overwrite each other.

Guard: devbox.sh apps refuses while any Deployment in apps lacks Argo CD's tracking annotation, and prints the command that hands them back. One owner per object is a platform rule, not a preference.

A rolling update that can never finish

Risk: Gitea's chart defaults to RollingUpdate with 100 % surge. Its SQLite volume is ReadWriteOnce; on a 4-node cluster the surge pod may land on another node, never mount the volume, and hang the rollout.

Fix: strategy: Recreate. Single-writer storage ⇒ stop the old pod first.

Rootless image, root-owned volume

Symptom: Gitea stuck in Init:CrashLoopBackOff: mkdir: can't create directory '/data/git/': Permission denied.

Cause: the rootless image runs as uid 1000; minikube's storage-provisioner creates hostPath volumes owned by root, and fsGroup is ignored for hostPath. On EKS (EBS + fsGroup) this wouldn't happen — a reminder that "works on my cluster" includes the storage driver.

Fix: a tiny root init container that chowns /data before the chart's own init runs.

Healthy pods, "Progressing" app

Symptom: gateway and frontend stuck at Progressing for 25 minutes with both pods 1/1 Ready; the other 8 were Healthy.

Cause: they're the two with an Ingress. Argo CD's built-in Ingress health waits for status.loadBalancer to get an address; on minikube the ingress-nginx LoadBalancer only gets one while minikube tunnel (sudo) runs.

Fix: a Lua health override in argocd-values.yaml: an Ingress is Healthy once it exists, and its message says whether it's routable. Health checks encode your definition of healthy — the defaults are someone else's.

Your own guardrails apply to your platform too

Symptom: seeding the env repo failed: pre-push: push to main is blocked.

Cause: a global git pre-push hook that protects main and blocks force-pushes on every remote — including the local Gitea, whose env repo deploys from main and whose devbox branch is force-updated on every push.

Fix: exempt exactly http://…localhost:3300/devbox/* from those two rules while keeping the secret scan. Narrow exceptions beat turning a guard off.

6Try it (10 minutes)

  1. make devbox-open, log in to Argo CD. Find the ten prod-like-* tiles. Open one and look at the resource tree: Deployment → ReplicaSet → Pods.
    All Synced + Healthy.
  2. Drift it: kubectl --context microecom -n apps scale deploy/bff-service --replicas=3. Watch the tile.
    OutOfSync for a moment, then back to 1 replica. Self-heal.
  3. Change the truth: in deploy/.run/env-config, add env: { LOGGING_LEVEL_ROOT: DEBUG } under apps.bff-service in envs/prod-like/services/bff-service.yaml. Commit and git push.
    Within 1–2 minutes (the 60 s poll plus Argo CD's repo cache; measured 101 s): a new pod with the env var. Check the Application's History tab. Impatient? Press Refresh on the tile — phase 2's devbox-ship does that for you.
  4. Undo it the GitOps way: git revert HEAD && git push.
    A third revision; the pod rolls back. Gitea's commit list for env-config is the change log.
  5. Delete a service file (git rm envs/prod-like/services/mock-paypal-service.yaml, commit, push), watch, then restore it with git revert.
    Prune removes the Application's objects; the revert brings them back.

7Interview questions

What's the difference between push-based CD and GitOps (pull-based)?

Push: a pipeline holds cluster credentials and runs kubectl/helm at the end of a build. Pull: a controller inside the cluster watches git and applies changes itself. Pull means CI never needs cluster credentials, drift gets corrected continuously instead of only at deploy time, and the cluster can be rebuilt from git alone.

Synced but Degraded — what does that tell you?

Argo CD applied exactly what git says, and what git says doesn't work (crashing image, failing probe, missing secret). The fix goes into git; re-syncing won't help.

Why can't you use Argo CD's "Rollback" button when auto-sync is on?

Rollback syncs an old revision while git still says the new one — auto-sync would immediately sync forward again. With auto-sync, rollback is a git operation (revert, or pin the old version), which also keeps the history honest.

Why keep config in a separate repo from application code?

Different change rates, owners and permissions: a deploy shouldn't need a code PR, and promoting a version between envs is a one-line config change. It also stops CI on the app repo from triggering itself when it writes a new tag.

What would you NOT put under GitOps, and why?

Secrets in plain text (use Vault/External Secrets/SOPS), and things whose desired state isn't declarative: data migrations, seed data, one-off jobs. Stateful infra can be GitOps'd but needs ordering (sync waves) and care with destructive diffs.

Two tools manage the same Deployment. What happens?

They fight: each apply overwrites the other's fields, and with server-side apply you get field-manager conflicts. Platforms enforce one owner per object — here, devbox.sh apps refuses to start while helm-owned apps exist.

Next — phase 2: versions you can roll back to

Right now every service runs tag dev, and every build overwrites it. So "roll back order-service" would pull today's image again — git history says one thing, the registry says another. Phase 2 gives each build a tag from its commit (order-service:9f8e7d6, or …-dirty-1009-1432 for uncommitted work), adds make devbox-ship and make devbox-deploy, a registry browser, and a cleanup that never deletes a tag an env still points at.
