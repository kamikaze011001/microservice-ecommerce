The contract, written down

Phase 6 of the devbox. Every endpoint's promise — status, shape, error cases — as plain text files you can click through in a GUI or run against any env. On its first live run it found a real bug.

A client of your API depends on more than the happy path: that a bad request is a 400 naming the bad field, that a missing token is a 401, that a forbidden route is a 403. Those promises are the contract — and they break silently, because nothing in the UI exercises them.

So write them down as tests, and run them after every deploy.

1Where it sits

k6 end-to-endPayPal redirects, saga, load — phases 4 / 3b
API contract (Bruno)each endpoint's status, shape and errors — this phase

The middle layer is the one that was missing. Unit tests mock the neighbours, so they can't see a 400 turning into a 500 between services; k6 checks that checkout works, not what an invalid request gets back.

3Run it — three ways, same files

Bruno GUI

Open api-tests/, environment local (needs the tunnel). Click, edit, add a request — it's a file in your diff.

make devbox-api-test env=…

The collection is streamed into a one-off pod in that env's namespace, so gateway:6868 is that env's gateway. Bruno CLI 4.2.1. Prints only failed tests with their reason.

After every ship

make devbox-ship runs it once the new version is live. SMOKE=0 skips it. A deploy that breaks a contract says so in the same command.

4What it found on day one

A client's mistake reported as a server error

Symptom: POST /bff-service/v1/cart:add-item without price → 500, Spring's default error body.

Cause: order-service correctly answered 400 with errors.price. bff calls it over Feign, and nothing handled FeignException — so every downstream error, including the caller's own bad input, became a raw 500, and the validation detail was thrown away. A storefront would show "something went wrong" instead of "price is required"; monitoring would count user typos as outages.

Fix: DownstreamExceptionHandler in bff — a downstream 4xx is passed through with its status and body; a 5xx or no answer is a 502 without internal URLs. Unit-tested (4 cases) and pinned by the Bruno test that found it.

Pinned, not changed: wrong password is a 400

Login with a wrong (well-formed) password answers 400 with code: "Your password is incorrect" — a sentence where a code belongs, and arguably a 401. The suite pins today's behaviour instead of silently "fixing" a product decision; changing it now shows up as a deliberate test change.

5What broke while building it

20 requests that didn't exist

The first in-cluster run reported 35 requests (20 skipped) for a 15-request collection. macOS tar adds an AppleDouble ._name.bru sidecar for each file; Bruno tried to read them. COPYFILE_DISABLE=1.

A failure report that listed passing tests

Bruno marks every non-2xx request — and half this suite is negative tests that expect 400/401/403 and pass. Reporting "non-2xx requests" listed six green tests as problems. The report keys on failed tests (✕) and prints the reason under each.

A patch that silently didn't apply

One scripted search-and-replace in devbox.sh didn't match (an escaping difference) and changed nothing — no error, because "replace" of a missing string is a no-op. The output simply didn't improve, which is how it was noticed. Edits that must apply should fail loudly when they don't.

6Interview questions

What's an API contract test, and how is it different from a unit test?

It calls the real, deployed API over HTTP and checks what a client relies on — status codes, response shape, error semantics — across service boundaries. Unit tests mock those boundaries, so they can't see what one service does with another's error.

Why test the error cases at all?

Clients branch on them: a 400 shows a field message, a 401 triggers re-login, a 403 hides a button, a 5xx retries or alerts. If a 400 becomes a 500, the UI shows the wrong thing and monitoring counts user mistakes as outages.

What should a gateway/BFF do with a downstream error?

Preserve its meaning: pass client errors (4xx) through with their detail; turn downstream failures into 502/503/504 for the caller; never leak internal hostnames or stack traces.

Bruno vs Postman?

Both are API clients with scripting and test runners. Bruno stores collections as plain text in your repo (reviewable, offline, no account); Postman centres on a cloud workspace and JSON exports. For tests that live next to the code and run in CI, the file-based model fits better.
