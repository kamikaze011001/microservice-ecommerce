Versions you can roll back to

Phase 2 of the devbox. Every build gets a name that means the same bytes forever. That's what makes "go back to yesterday's order-service" actually work.

Phase 1 put the history in git. But git only stores names — image.tag: dev. If the registry lets that name point at different bytes tomorrow, history is a lie: reverting the commit reverts the name, not the code.

So: a tag is a promise. Once order-service:ac48ad8 exists, it means those exact bytes, forever. Rollback = point the env at an older promise.

2How a service's tag is chosen

Tag = the last commit that changed the files that go into that image — not HEAD.

You…order-serviceinventory-servicefrontendWhy
commit a fix in order-service/new tagsamesameOnly order-service's inputs changed. The other nine aren't rebuilt and can't be rolled back by accident.
commit a change in core/newnewsameEvery JVM image contains the core JARs. The SPA doesn't.
edit order-service/ without committingac48ad8-dirty-1010-0932samesameUnique per build, traceable to a base commit, and visibly not reproducible from git.
edit README.mdsamesamesameNot an input of any image.

The inputs come from the Dockerfiles' COPY lines: a JVM service = its folder + core/ + Dockerfile.jvm + Dockerfile.cores. If you add a COPY, add the path to version_inputs in deploy/devbox/lib/version.sh, or a change there won't produce a new tag.

make devbox-deploy svc=order-service tag=dev — "put back that version": steps 5–7 only, after checking the tag is in the registry. That check matters: a commit naming a missing tag is a guaranteed ImagePullBackOff, and git would have recorded it as a "deploy".

Step 7 waits for this env commit, not just "Synced". "Synced" alone could be the previous commit that Argo CD hasn't noticed is old yet.

4Cleanup without breaking rollback

Every ship adds ~300 MB. make devbox-gc (dry run; APPLY=1 to act) keeps, per service:

Every tag an env pins

Read from the env repo. Removing it would break the next sync or pod restart.

dev

The bootstrap tag — always a valid way back.

The newest N (default 5)

Your recent rollback window.

Anything sharing a kept digest

The registry removes by digest, not by tag. Two tags on the same bytes go together — so a doomed tag that shares a kept one's digest is kept.

Then the registry's own garbage-collect frees the layers. The one sharp edge: git revert past the window brings back a tag gc already removed. devbox-deploy refuses that; a hand-made revert doesn't — check make devbox-tags first.

6What broke while building it

A proof that passed for the wrong reason

Symptom: the first devbox-proof went 6/6 PASS — ship ac48ad8, roll back to dev, roll forward. Then devbox-tags showed both tags with the same build time.

Cause: same digest. The old dev image had been built from exactly the inputs of commit ac48ad8, and Docker's layer cache reproduced it bit for bit. The "rollback" switched between two names for the same bytes. Every check compared tag strings, so it couldn't notice.

Fix: the proof now checks the running pods' imageID digest, asserts the rollback target is different bytes, and — when it isn't — builds one (same image + a label). Re-run: 7/7, at the byte level. Lesson: a test that checks the name of a thing, not the thing, will pass on a lie.

[[ … ]] && printf as the last line of a function

Symptom: make devbox-tags printed only its header and exited 1, after working fine the first time.

Cause: the helper that finds which envs use a tag ended with [[ $tag == $t ]] && printf …. With two tags, the last comparison is a non-match, so the function returns 1, and set -e kills the script without a message. With one tag it happened to match — which is why it worked before the first ship.

Fix: if … then printf; fi. Under set -e, never let a conditional be a function's last command.

Same inputs, same bytes — a feature

The flip side of the first scar: ship found order-service:ac48ad8 already built and skipped the build. Content-derived tags plus a deterministic build make "rebuild" a cache hit. That only holds while the tag's inputs list matches the Dockerfile's COPY lines.

7Try it

  1. make devbox-version svc=order-service, then edit any file in order-service/ and run it again.
    A commit hash, then <hash>-dirty-<now>. Undo the edit.
  2. make devbox-ship svc=order-service. Watch Argo CD's prod-like-order-service tile while it runs.
    A new image in the registry UI (localhost:8181), a commit "ship order-service dev → …" in Gitea, the tile goes OutOfSync → Synced.
  3. make devbox-tags svc=order-service, then make devbox-deploy svc=order-service tag=dev.
    The "← prod-like" marker moves; the pod rolls back.
  4. make devbox-deploy svc=order-service tag=doesnotexist
    Refused before anything is committed, with the list of real tags.
  5. make devbox-gc (dry run).
    Nothing pinned or recent is listed.
  6. make devbox-proof
    Seven PASS lines — including "rollback target is different bytes".

8Interview questions

Why are latest/dev tags a problem in production?

They're mutable: the same name points at different images over time. Rollback, audit ("what ran at 14:02?") and reproducibility all break, and different nodes can run different code under one tag depending on when each pulled.

Tag by commit or by digest?

A digest (@sha256:…) is the only truly immutable reference — even a commit tag can be re-pushed. Many teams deploy by digest and keep the commit tag for humans. Here, tags stay readable and the registry is local; pinning digests in the env repo would be the next hardening step.

With immutable tags, what imagePullPolicy should you use?

IfNotPresent is enough — a node that has :ac48ad8 has the right bytes. Always is only needed for mutable tags. The chart still says Always because the umbrella/AWS paths still use dev; with immutable tags it costs one manifest check per pod start and nothing more.

Why tag by the last commit that touched the service instead of HEAD?

Unchanged services keep their tag, so they aren't rebuilt or redeployed, and their history only shows real changes. The cost: the input list must match what the Dockerfile copies, or a change won't produce a new tag.

How do you keep a registry from growing forever without breaking rollbacks?

Retention that knows what's deployed: never remove anything an environment references, keep a recent window, remove by digest carefully (shared digests), then run the registry's blob GC. Harbor/ECR lifecycle policies do the same; the "what's deployed" part is the piece they can't know without you.
