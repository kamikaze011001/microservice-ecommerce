What an environment really is

Phase 3 of the devbox. The same code, twice, on the same databases and Kafka — and neither copy can see the other's orders.

An environment is not a copy of the code. It's a set of config values — namespace, database names, topic names, hostnames — plus the state those values point at.

So "make a second env" is mostly a search: find every value that names shared state, and make it a per-env setting. Miss one, and the two envs quietly share it.

3How per-env config reaches a service

Spring reads properties from a ladder of sources; higher wins. Vault sits low, so an env can override it without touching it:

command-line args
SPRING_APPLICATION_JSON ← the env repo's springConfig, rendered by the chart
OS environment variables ← looked fine, but can't name these keys (below)
config data: application.yml, Vault import ← shared values: secrets + prod-like defaults

Why not plain env vars?

Topics bind into a Map<String,String> whose keys contain dots and dashes: order-service.order.failed-status. The env var APPLICATION_KAFKA_TOPICS_ORDER_SERVICE_ORDER_FAILED_STATUS becomes the key order.service.order.failed.status — a new entry next to Vault's, which keeps being used. No error, no warning: the preview would publish to prod-like's topic. JSON names the key exactly. EnvOverridePrecedenceTest pins it, and fails if you swap in the look-alike key.

make devbox-env-delete name=x APPLY=1 runs it backwards: remove the folder → the ApplicationSet deletes the Applications → their finalizer deletes what they deployed (without it the Deployments would be orphaned) → only then connector, topics, groups, schema subjects, databases, namespace. Apps first, so nothing is writing while its data disappears. Without APPLY=1 it only prints what it would remove.

5What broke while building it

A Vault token in the web server

Symptom: rendering a preview's frontend showed VAULT_TOKEN=root, JVM flags and the env-wide SPRING_APPLICATION_JSON on the Caddy container.

Cause: the chart kept the JVM defaults' env out of the static SPA with env: {} — a rule that only held while the frontend set no env of its own. The first one (API_BASE_URL) flipped it, and the defaults flowed back in.

Fix: in the chart, a static: true service never inherits defaults.env or springConfig — by kind, not by an empty map. Render-test now asserts the preview frontend carries none of them. An "it works because this field is empty" rule is one edit away from a leak.

A password one commit away from git

The first generated env.yaml overrode spring.data.mongodb.uri to point at the preview's database — and the URI carries the Mongo password. It would have been committed to the env repo. Fix: override only spring.data.mongodb.database (Spring prefers it over the URI's path), and a guard in env_gen.py that refuses to write any value with user:pass@ in it — tested in render-test.

A proof that failed for the wrong reason

Symptom: the first devbox-env-proof went 12/13 — every isolation and cleanup check passed, but "every preview order completed" read 80/90.

Cause: the load script approves 90%, cancels 5% and fails 5% of payments on purpose, to exercise the saga's compensation paths. 10 of 90 ending CANCELED/FAILED is the system working. The invariant was wrong, not the env.

Second try: "every order settled — none PROCESSING". It failed again: 4 orders PROCESSING. Reading the orchestrator explained it: a PayPal cancel abandons the payment attempt, not the order — the saga waits in AWAITING_PAYMENT for a retry, and only the 30-minute saga TTL cancels it. Correct by design; prod-like's own 7 PROCESSING orders were timed out to CANCELED during the same session.

Fix: a PROCESSING order is legitimate only if its saga is AWAITING_PAYMENT, not expired, with a CANCELED payment and no successful one — one SQL join. Anything else is "unexplained" and fails. Phase 2's proof once passed while proving nothing; this one failed twice while everything was right. Same bug both ways: an assertion that doesn't match what the system is designed to do. Read the workload and the state machine before writing the check.

Deleting an env shakes the shared broker

Right after a delete, the cluster API timed out and prod-like's services climbed to 0.5–0.9 CPU with no traffic. Their logs showed Kafka DisconnectExceptions and consumer-group rebalances: deleting 14 topics on a one-broker cluster that also hosts prod-like makes every consumer rebalance at once, on CPU-starved nodes. It settled by itself within minutes (Kafka 970m → 43m CPU, groups Stable), and prod-like's data and offsets were untouched. Shared infra means an env's lifecycle is never fully invisible to its neighbours — that's the price of logical isolation over separate clusters.

Golden files are evidence, not caches

Making app hosts namespace-relative changed resolved secrets, and the equivalence test (resolved output vs a frozen capture of the deleted legacy scripts) failed. Regenerating the golden would have erased the proof that the migration was faithful. Instead: deploy/secrets/tests/deviations/k8s.jq — each deliberate change, with its reason, applied to the golden before diffing.

7Interview questions

What makes two environments isolated, beyond separate namespaces?

Every piece of shared state they touch: databases, topics and consumer groups, caches, schedulers' locks, object storage, external callbacks. A namespace isolates workloads and DNS; it does nothing for a Kafka topic both envs name the same.

Two envs share a Kafka topic. What breaks?

Same consumer group: they split the partitions and each env processes the other's events. Different groups: both process every event — double side effects. Either way one env's actions show up in the other.

Why per-env logical databases instead of a database server per env?

Cost and speed: a database is a CREATE DATABASE; a server is gigabytes and minutes. The isolation is the same for an app that only ever names its own database. Production-grade isolation (noisy neighbours, versions, blast radius) is when you'd split servers.

How do you keep env-specific config out of the image?

Build once, configure at deploy time: the same image everywhere, with config injected by the platform (env vars, mounted files, a config service). Anything baked at build time — like the SPA's API URL today — forces an image per env. Phase 3c fixes exactly that.

Where must secrets NOT go in a GitOps setup?

In the config repo, in plain text — including inside URLs. Keep them in a secret manager and reference them; add guards that fail when a value looks like a credential.
