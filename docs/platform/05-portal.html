A portal is just a client

Phase 5 of the devbox. One page shows every env and service, what git says vs what's running, the change history and recent perf runs — and changes a version with one click, as a commit.

The portal owns no state. Everything it shows lives somewhere else: versions in git, health in Argo CD, images in the registry, perf runs in VictoriaMetrics. It is a client of the platform — the same thing a Backstage plugin is.

That's why it can be small, why it can't drift from the truth, and why deleting it loses nothing.

1What it does

Per env, per service

Git's pinned tag, the running image(s), Argo CD sync + health, and a "≠ git" flag while a rollout is still catching up.

Deploy a version

A tag picker (pinned tags first, marked "← prod-like"), one button, a confirm — and a commit in the env repo. Same rules as make devbox-deploy.

History

The env repo's commits for that env: every ship, deploy, rollback, create — who, what, when.

Perf runs

The runs make devbox-perf recorded, with PASS/FAIL.

make devbox-portal builds and deploys it; make devbox-open → http://localhost:8282.

3The one write — and its guards

1 · validateenv/service names, tag grammar
→
2 · readthe service file + its blob sha
→
3 · same tag?no-op, nothing committed
→
4 · registrytag must exist (422 otherwise)
→
5 · commitwith the sha read in 2 (409 if it changed)
→
6 · nudgeArgo CD refresh — best effort

Optimistic concurrency

The write carries the blob sha it read. If a CLI ship or another tab changed the file in between, Gitea refuses and the portal says "reload and try again" — it never overwrites someone else's change.

A text edit, not YAML

Parse → serialize would drop every comment in the env repo. The tag line is rewritten in place — the live commit was a one-line diff, comments intact.

The commit is the deploy

If the refresh nudge fails, the deploy still succeeded: Argo CD picks the commit up on its 60 s poll. The response says refreshed: false instead of pretending it failed.

Names can't become paths

Env and service names are validated to [a-z0-9-] before they touch a Gitea path — .., /, uppercase: 400.

4What broke while building it

A rollout that fed on itself — and the platform's own rollback

Symptom: the first live deploy through the portal (order-service ac48ad8 → dev — byte-identical images!) never finished. The API server timed out, nodes ran at 1–2.25 of their 4 CPUs, and ps inside the nodes showed order-service JVMs that were 6–13 seconds old, on two nodes at once.

new pod: JVM start ≈ 1.5 CPU
→
HPA reads startup CPU as load → 3 replicas
→
more JVM starts on starved nodes
→
startup outlasts the liveness window → restart
↺

Evidence vs inference: the young JVMs and the HPA left at 3 replicas while reporting 6% CPU are measured; the liveness kills are inferred — the API was down, so no events were captured.

Recovery: the platform's own golden path — pin the old tag from the portal. Back on the healthy ReplicaSet in ~135 s; the env repo records deploy and rollback. Follow-up (chart, separate PR): a startupProbe so a slow JVM start isn't a liveness failure, and an HPA scale-up stabilization window so startup CPU can't trigger it.

Every file read would have been a 404

Gitea paths went into a {path} URI-template variable, and Spring encodes a variable's / as %2F. The mock-server test caught it before anything ran live. Fix: the (pre-validated) path joins the template as literal segments.

An API parameter that's silently ignored

Gitea's commits endpoint ignores limit when the query is filtered by path — limit=3 returned 12. The cap is enforced client-side now, with a test. Read what an API does, not what its docs list.

A port-forward pinned to a pod that no longer exists

kubectl port-forward service/x resolves to one pod when it starts. After redeploying the portal, the forward pointed at the deleted pod ("lost connection to pod") while its PID file still looked alive — and a wait-until-reachable loop spun forever. make devbox-portal now re-opens the forward after every rollout.

5Try it

  1. make devbox-portal, then open http://localhost:8282.
    One section per env; every service Synced/Healthy; history on the right.
  2. Pick a tag for a service and Deploy. Watch the row.
    "≠ git" while it rolls, then the running tag matches; a new history entry "deploy … (pinned from devbox-portal)".
  3. Open the same page in two tabs, deploy from one, then deploy from the other without reloading.
    The second one answers 409 — "changed since it was read". No lost update.
  4. curl -XPOST localhost:8282/api/envs/prod-like/services/order-service:deploy -H 'content-type: application/json' -d '{"tag":"nope"}'
    422, and nothing in the env repo.

6Interview questions

What is an internal developer portal, and what should it own?

A UI over the platform's sources of truth (catalog, deploy state, docs, metrics). It should own as little as possible — ideally nothing — so it can't disagree with the systems it shows. Backstage is the common open-source one; its plugins are exactly "clients" like this.

Why do a deploy as a git commit from a UI, instead of calling the cluster?

One path for every change (CLI, UI, CI): audited, reviewable, revertible, and the GitOps controller stays the only writer to the cluster. A UI that calls kubectl creates drift the controller then reverts.

How do you prevent lost updates when two people edit the same config?

Optimistic concurrency: read a version (here the git blob sha), write conditionally on it, and on conflict re-read and retry or ask the user. Same idea as ETags/If-Match or a version column.

Why can an autoscaler make a rollout worse?

Startup work (JIT, class loading, connection pools) looks like load. On constrained nodes that triggers scale-up, which adds more startup work. Use startup probes, scale-up stabilization windows, CPU-based HPA with realistic requests — or scale on a business metric.
