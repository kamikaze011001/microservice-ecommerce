"Is my change slower?" as one command

Phase 4 of the devbox. Every load test is tagged with the exact code it ran against, so comparing two runs also tells you what changed between them.

A latency number on its own is trivia. "p95 went from 57 ms to 62 ms" only means something next to "…and the only change was order-service ac48ad8 → 9f8e7d6" — or "…and nothing changed", which makes it noise.

Phases 1–3 made what's running a fact in git. Phase 4 stamps that fact onto every perf run.

1The golden path

make devbox-perf scenario=payment                # smoke against prod-like
make devbox-perf scenario=payment env=preview-cart profile=load
make devbox-perf-runs
make devbox-perf-compare a=prod-like-payment-1010-104742 b=prod-like-payment-1010-104818

2Noise — play with it

Two runs of identical code never match exactly. How big a difference is real depends on how many requests the p95 is computed from.

requests per run: 5
run A p95
run B p95

Same latency distribution both times; only sampling differs. With a handful of requests the p95 is one unlucky request — that's why compare marks rows under 30 requests. For decisions, use profile=load (thousands of requests), run each side more than once, and compare like with like: a preview's pods are smaller than prod-like's, so cross-env deltas measure the pods, not your code.

Why VictoriaMetrics is the only store

No local results file to lose, and the Grafana dashboard reads the exact same series as the CLI. A run's metadata is one sample of devbox_perf_run, pushed through VM's import API.

Why the last sample is the whole run

k6's Prometheus output computes trend stats (p95, avg…) over the whole test so far. So last_over_time(k6_http_req_duration_p95{devbox_run=…}) is the run's overall p95 — checked against k6's own summary: 56.93 ms ↔ 57 ms.

Thresholds decide PASS/FAIL

The scripts already declare SLOs (p(95)<2000 for create_payment, error rate < 5%). k6 exits 99 when one is breached; that exit code is the run's recorded value. Gating a ship on it is one && away.

Setup isn't the workload

Admin login and inventory top-up run once in k6's setup(); they're excluded (group!="::setup") so they don't distort the per-request table.

4What broke while building it

"No recorded run" — for 30 seconds

Symptom: straight after the second run, devbox-perf-compare said the run didn't exist. Retrying "a few minutes later" failed too — so I dropped my first hypothesis.

Cause: the first hypothesis was right. VictoriaMetrics hides samples younger than -search.latencyOffset (30 s) from queries. The timestamps showed the retry had run 31 s after the run — the "few minutes" was my sense of time, not the clock.

Fix: devbox-perf returns only once its run record is queryable. Lesson twice over: a TSDB's "now" lags real now, and check timestamps before discarding a hypothesis.

A failed threshold that would have vanished

The k6 call ran under set -e. A breached threshold (exit 99) would have aborted the script before recording the run — so exactly the runs you most need to see would leave no trace. || code=$?: a failure is a result to record, not a reason to stop.

5Try it

  1. make devbox-perf scenario=payment twice, then compare the two run ids.
    "none — same code": your noise floor.
  2. Change something in order-service/ (or ship a branch), make devbox-ship svc=order-service, run perf again, compare with the last run.
    "order-service ac48ad8 → <new tag>" under versions that differ.
  3. make devbox-perf scenario=payment profile=load (5 min, 50 users).
    Thousands of requests per endpoint — no noise flags.
  4. make devbox-open → Grafana → Devbox — perf runs; pick run A and run B.

6Interview questions

Why p95/p99 instead of average latency?

Averages hide the tail; users feel the tail. One slow dependency can leave the average flat while 5% of requests time out. p95 says "19 of 20 requests were at least this fast".

How do you know a perf regression is real?

Know your noise floor first (same code, several runs), use enough requests per endpoint, hold the environment constant, change one thing, and repeat. A delta smaller than the noise floor isn't a finding.

Where should perf tests run in a delivery pipeline?

Smoke-sized checks with thresholds on every deploy to a prod-like env (cheap, catch big regressions); full load tests on a schedule or before releases. Results tied to the deployed versions, or nobody can act on them.

Why tag metrics with versions instead of keeping a results spreadsheet?

The tag travels with the data: any dashboard, alert or query can slice by version without joining to an external record that drifts. The cost is label cardinality — fine for one label set per run, not per request.
