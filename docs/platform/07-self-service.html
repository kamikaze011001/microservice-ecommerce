A developer should never need the CLI

Phase 7a of the devbox. The portal becomes the front door: create and delete preview envs with a button, watch every step live, deploy or roll back a version — no make, no kubectl, no port-forwards.

Devbox · platform engineering series · 7a

Phases 1–6 built the golden paths: proven, repeatable ways to create an env, ship a version, run a test. But they were make targets — a developer had to learn them. A platform isn't done until its golden paths are self-service: discoverable and one click away.

The trick is to not rewrite them. The portal starts a Kubernetes Job that runs the exact same script the CLI runs, and streams its log. One implementation, two front doors.

1What you can do from the UI now

Create a preview env

+ New preview env → name it → watch namespace, databases, topics, CDC connector, Redis, seeds and all 11 services come up, step by step. The button explains itself when it's disabled (cap reached, a job running).

Delete one

Type the env's name to confirm; every piece it owns is removed. prod-like can't be deleted.

Deploy / roll back

Every service's versions are loaded up front (the old page's empty-first-click bug is gone); confirm in a dialog that tells you how to undo.

Jobs

Everything the portal ran, with status, duration and the full coloured log — kept 7 days.

Open the env

Storefront and API-docs buttons per env; Argo CD, Gitea, Grafana and the registry in the sidebar — by name, through the ingress.

History

Per env, every change as a commit — now authored devbox-portal when the portal made it.

2How it works

Button → POST /api/jobs {kind, target}
→
portal creates a Job (image devbox-runner)
→
runner: devbox.sh env-create preview-x
→
page polls /api/jobs/{name}/log every 2 s
  • The runner image is deploy/ + the seed images + kubectl, jq, git, python3. It's tagged like every service: the last commit that touched its inputs.
  • In-cluster mode (DEVBOX_IN_CLUSTER=1) is the only change to devbox.sh: Gitea by Service DNS instead of a localhost port-forward. Everything else already went through the API server.
  • The Job is the record. Labels say what ran against which env, status says how it went, the pod keeps the log. The portal still owns no state.

3Why a button that runs cluster-admin work is safe here

  • No command lines. A request names a kind from a fixed list (JobKind); each maps to fixed arguments. The env name must match the preview grammar. {"kind":"shell"} is a 400.
  • One at a time. Env jobs share the env repo and the preview cap, so a second one is a 409 until the first finishes.
  • No retries of half-done work (backoffLimit: 0): a failed step is reported, and a re-run is safe because every step checks what already exists.
  • Least privilege for the portal itself: it may create Jobs and read their pods' logs in devbox only. The runner's ServiceAccount has cluster-admin — acceptable on a single-user laptop cluster, and called out in k8s.yaml.

4What broke while building it

A job that said SUCCEEDED while half its work failed

Symptom: the first portal-created env reported success; the log showed ✗ refusing to seed: … current context is '<none>' — twice.

Two causes. (1) The runner defined its kube context but never selected it, and seed.sh guards against seeding the wrong cluster by checking the current context. (2) The real bug: devbox.sh ran seed.sh … && log_ok. Under set -e a failure inside an && list doesn't stop the script — so the env came up with no routes' roles and no stock, and nobody was told. It had always been that way on the CLI too.

Fix: every seed and connector step is now || { log_err …; return 1; }. The next run failed loudly on the next gap — the product images live in docker/seed-images, outside deploy/ — which went into the runner image. Same lesson as the inventory fix (PR #81): a step that can't do its job must fail, never log and move on.

The tag picker that was empty on first click

The old page fetched a service's tags on the dropdown's focus — the browser opened the list before they arrived, and the 30 s refresh could close it. Tags now load for every service with the page, and the choice lives in the row's component, so a refresh can't reset it.

5Try it

  1. Open http://localhost:8282 (or http://devbox.microecom.local with the hosts entries and tunnel).
    Sidebar: Environments, Jobs, Perf runs; platform tools at the bottom.
  2. On a preview env, Delete → type its name.
    You land on the job's live log; it ends with "deleted (databases dropped, namespace … gone)".
  3. + New preview env → cart → Create.
    5–10 minutes of log, ending "preview-cart is up"; Environments shows it with 11/11 healthy.
  4. While it runs, try to create another.
    The button is disabled and says which job you're waiting for.
  5. Deploy an older tag of any service, then deploy the previous one back.
    Two commits in that env's history, both by devbox-portal.
