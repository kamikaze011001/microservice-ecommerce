# Session 2026-08-01 — deploy structure refactor: design spec + Plan 1

## Context
The AWS live bring-up (2026-07-24) exposed the real problem: three deployment targets
(docker-compose, kind k8s, EKS) with **three divergent code paths** for the same concerns.
Secrets are duplicated 2–3× (`docker/vault-configs/*.json` vs
`k8s/infra/jobs/03-vault-seed/seed.sh` vs `scripts/aws/seed-secrets.sh`), install scripts
overlap ~60% (`k8s/infra/install.sh` vs `scripts/aws/infra-up.sh`), seed logic is triplicated,
and there are three command dialects (`make up` / `make k8s-*` / `make aws-*`). The drift has
already cost multiple documented crashloops (`k8s/CLAUDE.md` scars).

## Done
- **Brainstormed + approved the design** →
  `docs/superpowers/specs/2026-08-01-deploy-refactor-design.md` (commit `730f10f`).
  Six decisions settled (Q1–Q6): three first-class envs, one Helm umbrella chart for k8s,
  per-env secret backend abstracted by the chart, parametrized images with immutable EKS tags,
  keep the 4 namespaces, canonical env-aware seed scripts run outside Helm. Full rationale table
  in the spec. Also: target `deploy/` tree, 9-phase migration plan, move/delete inventory,
  5 open questions, explicit non-goals.
- **Wrote Plan 1 (Foundation)** →
  `docs/superpowers/plans/2026-08-01-deploy-foundation.md` (commit `e041fe2`).
  Covers spec Phases 0+1 only: scaffold `deploy/`, replace kind with minikube, keep kustomize
  untouched. 10 tasks with per-step verification + acceptance criteria.
- **Verified the minikube registry mechanics from the addon source** (this is the load-bearing
  detail of Plan 1): `minikube addons enable registry` deploys a registry Deployment, a
  **ClusterIP** Service (80 → 5000), and a `registry-proxy` **DaemonSet** (hostPort 5000 on every
  node). So pods pull `localhost:5000/<svc>:dev` with no containerd `hosts.toml` patching (unlike
  kind), but the host **cannot** push directly — the Service is ClusterIP. Hence `cluster.sh`
  manages a background `kubectl port-forward -n kube-system svc/registry 5000:80` via a PID file.
  Same image reference on both sides; registry port moves 5001 → 5000.

## Decisions
- **Helm scope is "everything k8s", not literally everything** — docker-compose can't be
  Helm-managed, so it keeps its compose files but shares the canonical artifacts
  (`deploy/secrets/`, `deploy/seed/`, `deploy/images/`) with minikube + EKS.
- **Seed stays outside Helm** — Helm hooks vs app-rollout ordering can't express "seed MySQL
  after ddl-auto created the schema". Helm owns manifests, scripts own data.
- **Drift prevention is a check, not a doc** — `deploy/scripts/secrets-validate.sh` runs as a
  pre-flight of `make secrets-seed` and fails on key-set drift. The scars become a failing build.
- **Migrate build-new-alongside-old**; deletion of `k8s/` + `aws/` is Phase 8, only after
  `make bootstrap ENV=k8s` and `ENV=aws` both pass.
- **minikube ingress = LoadBalancer + `minikube tunnel`**, replacing kind's
  `extraPortMappings` + hostPort. `/etc/hosts` entries stay valid (tunnel assigns 127.0.0.1).

## Scars earned
- **`k8s-seed-mysql` must run AFTER `k8s-apps`.** Running it first fails the job (schema comes
  from Hibernate `ddl-auto` at service startup). The constraint is documented at `Makefile:282`;
  it was ignored this session and cost a 5m job timeout. Correct order:
  `k8s-seed` → `k8s-apps` → `k8s-seed-mysql` → `k8s-seed-inventory` → `k8s-seed-images` →
  `k8s-seed-perftest`.
- **Background `make` without `tee` gets reaped silently.** The first `k8s-infra` run vanished
  leaving a 42-byte log and three unapplied manifests, while looking like nothing was wrong.
  Always pipe through `tee`.
- **Do not announce a root cause from a partial/lagging log.** I claimed helm would deadline on a
  `<pending>` LoadBalancer without `minikube tunnel` and proposed dropping `--wait`. Helm v4.2.0
  marked the release `deployed` with `EXTERNAL-IP <pending>` and continued normally. The fix was
  never applied because the premise was false. This is the exact failure mode `k8s/CLAUDE.md`
  already warns about.
